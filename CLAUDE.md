# CLAUDE.md — instructions for coding agents

LLM Gladiator Arena: a deterministic turn-planning duel game. Two LLMs submit JSON battle plans; a simulator resolves up to 12 ticks on a 7×7 grid; the browser shows a replay and produces logs/prompts for the next round. There are also a headless CLI and a tournament runner sharing the same engine.

## Read first

- `docs/RULES.md` — canonical ruleset v2: tick phases, timing conventions, edge-case policies. Gameplay changes start here.
- `docs/TARGET_ARCHITECTURE.md` — module boundaries and the dependency rule.
- `docs/VIBE_CODING_GUIDE.md` — the change loop and prompt templates; follow its "definition of done".
- `docs/PLATFORM_STATUS.md` — what is implemented; `docs/decisions/` — ADRs for choices that should not be relitigated.

## Facts that must stay true

- **Canonical source is `src/`.** `dist/`, `release/`, and everything under `legacy/` are generated or archived artifacts — never edit them, never trust `legacy/` as reference for current behaviour.
- **The engine is deterministic and browser-independent** (ADR 0001). No `Math.random()`, `Date.now()`, DOM, storage, network, or provider imports anywhere under `src/engine/` or `src/domain/`. Identical plans + state must produce identical results. If a feature needs randomness, it must be seeded from the match input.
- **Structured events are the replay API** (ADR 0002). The engine emits typed `CombatEvent`s; prose is produced only by formatters in `src/presentation/`. Never parse log text to recover game state.
- **Contracts are versioned** (ADR 0003). Changing plan/state/event shapes requires a schema decision and migration support; changing combat behaviour requires a `RULESET_VERSION` decision in `src/domain/rules.ts`.
- **Validation is forgiving by design.** Malformed LLM output degrades to `idle` with a warning; it never hard-fails a whole plan. Do not "fix" this into strict rejection.
- **Rules, prompts, and help must not drift.** Ability metadata lives in `src/domain/abilities.ts` + `src/domain/rules.ts` and feeds validation and prompt generation. If the LLM prompt disagrees with the engine, every match is silently corrupted — this is the highest-severity class of bug in this project.
- **Timing convention:** cooldowns/effects decrement at the start of each tick, and an effect's duration includes the tick it was applied (so "this tick and next" = duration 2). See `docs/RULES.md`.

## How to verify a change

```powershell
npm.cmd test            # vitest: engine scenarios, properties, contracts, tournament, UI/a11y
npm.cmd run typecheck   # tsc --noEmit
npm.cmd run build       # production build to dist/
```

All three must pass before completion (CI enforces them on push). For gameplay changes, add or update a scenario test first. Then exercise the browser flow: `npm.cmd run dev`, load samples, Simulate, step the replay, Carry final state, simulate again.

The sample duel is pinned as a golden fixture (final HP A=75 / B=100, outcome `B_leading`). If your change legitimately alters it, update the fixture and bump `RULESET_VERSION` in the same commit, and say so in your report.

## Scope discipline

- Keep structural refactors, behaviour fixes, and balance changes in separate commits.
- Fixing a gameplay bug changes match outcomes; say so explicitly in your report.
- Never place API keys or provider calls in client code; model integration goes behind the `FighterAgent` adapter (ADR 0004).
- Releases are generated by `npm.cmd run release` (ADR 0005) — never hand-edit files under `release/`.
